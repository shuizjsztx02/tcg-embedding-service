# TCG 卡牌视觉匹配服务技术方案 v1

日期：2026-08-26
目标：用户上传一张真实拍摄的宝可梦卡牌照片 → 返回库中唯一完全一致的卡；不在库中则拒绝。准确率目标 95%。

## 0. 结论先行

- DINOv2 路线方向正确，但"裸 DINOv2 + 余弦相似度"在真实照片上大概率到不了 95%。真正扛指标的是三件事：**预处理（卡片定位/矫正/方向）**、**用"模拟手机拍照"增强做对比学习微调**、**拒绝阈值校准**。
- 库现状：9435 张干净扫描图，分辨率仅 200×279，且混有 90° 旋转的图。文件名带 `_200w`，强烈暗示这是缩略图，**很可能存在更高分辨率的原图**——如果能拿到，这是杠杆最大的单项改进（卡号、系列标志等细粒度信号在 200px 下几乎不可读）。
- 本机无 GPU。微调需要一块 GPU（云/Colab 即可，单卡几小时）；推理可以纯 CPU（ONNX），单请求 P95 可控制在 300ms 内。
- 9.4k 向量的检索不需要花哨索引，暴力余弦就是毫秒级。

## 1. 问题定义与验收口径

- 已知卡准确率：库内卡的真实照片，top-1 命中率。
- 拒绝准确率：库外卡（其他系列、其他 TCG、非卡物体）的拒绝率。
- 系统准确率 =（已知卡判对 + 库外卡拒对）/ 总数，**以真实照片测试集（协议 C）≥95% 为最终验收口径**。模拟照片（协议 A/B）用于过程迭代。

## 2. 现状盘点（实测事实）

- `images/` 共 9435 个文件；主流分辨率 200×279，少量 220×307 与横向 200×14x（横向实为旋转 90° 的竖卡，已目视确认）。
- 每卡单图、无重复；无真实照片样本；无元数据文件。
- 环境：Python 3.13，torch 2.13 CPU-only，无 GPU。

## 3. 总体架构

```
离线建索引:
images/ -> 数据治理(方向修正/去重/元数据csv) -> 预处理P(.) -> DINOv2(微调后) -> L2归一化
        -> index/embeddings.npy + ids.json (带版本号)

在线API:
上传图 -> 同一套预处理P(.) -> 同一模型 -> 向量 -> 暴力余弦top-K
      -> 阈值/margin判定 -> {card_id, score} 或 REJECT
```

关键原则：gallery 与 query 走完全相同的预处理与模型代码路径。

## 4. 支柱一：数据治理与预处理

M0 数据治理：
1. 方向修正：横向图旋转为竖卡（产出 normalized 副本，不动原图）；
2. 解析 ID、产出 `csv/metadata.csv`（id, filename, orientation, resolution, sha1），用于去重与按系列切分；
3. 确认是否存在高分辨率原图（最高优先级事项）。

预处理管线（OpenCV，离线/在线共用）：
1. EXIF 方向修正；
2. 卡片四边形检测：轮廓 + approxPolyDP，回退 minAreaRect，再回退按先验比例中心裁；
3. 单应性矫正到标准 63:88 比例；
4. 180° 方向修正：小分类器（库图 + 旋转增强训几百样本即可）；
5. 轻度质量增强：白平衡、高光抑制、轻锐化——保守，不引入伪影；
6. 等比 resize + padding 到模型输入方形。

## 5. 支柱二：模型

阶段 1（M1，baseline）：裸 DINOv2 ViT-B/14，CLS+mean-pool 拼接，L2 归一化。出基线数字 + 混淆分析（重点看"同画不同卡"错配）。

阶段 2（M2，核心）：对比学习微调
- 正对 = 同一张卡的"扫描视图" vs "模拟手机拍照视图"；负例 = batch 内其他卡 + memory bank semi-hard 负例；损失 InfoNCE。
- 模拟手机视图（缩小 domain gap 的关键）：透视扭曲、眩光条带、高斯/运动模糊、噪声+JPEG 压缩、色温亮度抖动、桌面背景、边缘遮挡/裁剪、二次降采样。
- 细粒度硬负例：batch 组batch 时优先同宝可梦/同系列的卡（若元数据可得），逼模型学系列标志/卡号/稀有度差异。
- 规模估算：9435 卡 × 2 视图，batch 128 卡 → 每 epoch ≈74 步，60–100 epoch ≈5–8k 步；ViT-B 448px + 梯度检查点，单张 24GB GPU 几小时；算力紧则 LoRA。
- 输出头：CLS+mean 拼接 → 线性投影 512 维 → L2 归一化。

阶段 3（可选，由混淆分析触发）：两阶段高分辨率 rerank（224 粗排 top-10 → 448 patch token 细排）；或 OCR 卡号校验（依赖拿到更高分辨率库图）。

## 6. 支柱三：检索与拒绝

- 索引：numpy / faiss IndexFlatIP 暴力，9435×512 float32 ≈19MB，毫秒级。
- 判定：top-1 分数 s1、top-2 分数 s2。接受 ⇔ s1 ≥ τ 且 (s1−s2) ≥ m；τ、m 在验证集校准。
- 校准数据：留出"未知系列"（按系列切分，不参与训练）+ 非卡图片校准 τ，杜绝泄漏。
- 返回置信分层：matched / low-confidence / rejected，提供 strict 模式。

## 7. 评估协议

- 协议 A（模拟真拍，迭代用）：留 10% 卡，每卡 5 个模拟视图，对剩余索引测 top-1/top-3。评估模拟器参数分布与训练不同，防止"自己验自己"。
- 协议 B（未知拒绝）：留出系列 + 外部图片，测误接受率。
- 协议 C（真实照片，验收用）：收集 300–500 张带正确 ID 的真拍（不同人/设备/光照），最终验收。
- 延迟：端到端 P95。

## 8. 工程设计

- FastAPI + ONNX Runtime（CPU）+ opencv-python-headless + numpy/faiss-cpu。
- `POST /v1/match`（multipart）→ `{status: matched|rejected, card_id, score, margin}`；`GET /v1/health`；离线 `script_temp/build_index.py`。
- 产物目录：`index/`（npy+ids+版本）、`models/`（onnx）、`csv/` 元数据、`doc/` 文档、`script_temp/` 脚本。
- 延迟预算：预处理 ≤50ms，embedding ~100–200ms（224 CPU ONNX），检索 ≤5ms。

## 9. 里程碑

| 阶段 | 内容 | 验证 |
|---|---|---|
| M0 | 数据治理 + 元数据 | csv 产出、方向修正、去重确认 |
| M1 | baseline + 评估脚手架 | 协议 A/B 基线数字 + 混淆分析 |
| M2 | 微调 + 阈值校准（需 GPU） | 协议 A ≥95%、B 误接受 ≤5% |
| M3 | 服务化 + 真拍验收 | 协议 C ≥95%，P95 延迟达标 |

并行工作流：真实照片收集从现在就开始，不阻塞 M0–M2。

## 10. 风险与待确认问题

1. 是否存在高分辨率原图？（`_200w` 命名暗示是缩略图）——对"同画不同卡"的区分是决定性因素。
2. 训练 GPU 从哪来？（云单卡 24GB 足够，几小时量级）
3. 真实照片能收集多少？覆盖几种设备/光照？
4. "完全一致"的业务定义：闪卡/反闪/重印算同一 ID 还是不同 ID？库内是否已区分？
5. 部署环境：CPU 还是 GPU 服务器？并发量级？
