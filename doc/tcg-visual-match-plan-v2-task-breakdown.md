## 二、总体任务拆解

### Task 0: 数据治理与质量加固

**做什么**:
1. 修复 01_data_audit.py：对每张图片做完整解码校验（img.load() + np.array），发现真正的损坏图片
2. 方向修正：对 546 张 landscape 图做旋转（产出 normalized 副本或记录旋转元数据）
3. 在 preprocess.py 中增加"完整解码校验"逻辑，供后续脚本复用
4. 产出 csv/metadata.csv：包含 id, filename, orientation, width, height, sha1, valid

**验收标准**:
- 所有 landscape 图的方向已明确（通过文件名或元数据记录）
- 损害图片清单已产出，可被后续脚本跳过
- 每张图片确认可完全解码

**测试方法**:
- 运行修复后的 audit 脚本，观察 corrupt count
- 随机抽 10 张 landscape 图目视确认方向
- 对比修复前后 rows 数量差异

**堵点与风险**:
- 如果大量图片存在截断问题（PIL 懒加载通过但 load() 失败）——需要决定是否修复/替换这些图片
- 200px 的低分辨率是关键瓶颈——高分辨率原图如果能拿到，对准确率提升最大

### Task 1: 基线评估（M1）

**做什么**:
1. 安装缺失依赖：faiss-cpu, transformers, opencv-python-headless
2. 运行 02_baseline_eval.py 获取裸 DINOv2 的基线数字
3. 分析混淆矩阵：哪些种类的卡容易被误判？"同画不同卡"（同一宝可梦不同编号）的错配率？
4. 输出评估报告到 doc/baseline-report.md

**验收标准**:
- 基线 top-1 准确率数字已出（模拟真拍场景）
- 已知卡命中率、未知卡拒绝率、分数分布（genuine/miss/impostor 的 P5/P50/P95）
- 混淆分析有了结论

**测试方法**:
- python script_temp/02_baseline_eval.py --n-query 500 --n-unknown 200
- 检查 csv/baseline_eval.csv 产出
- 对结果做可视化分析（分数分布直方图）

**堵点与风险**:
- CPU-only 环境下，500x2 张图的 embedding 计算时间较长（ViT-B/14 约 200ms/张 → 200s 左右）
- 200px 分辨率下，DINOv2 的 patch 是 14x14，224px 输入只有 16x16=256 个 patch，信息量有限
- 基线数字可能不理想（裸 DINOv2 对真实照片的 domain gap 大概率 > 10%）

### Task 2: 预处理管线完善

**做什么**:
1. 将 preprocess.py 扩展为完整的预处理管线，离线/在线共用：
   - EXIF 方向修正
   - 卡片四边形检测（轮廓 + approxPolyDP）
   - 单应性矫正到标准比例
   - 180° 方向修正（小分类器）
   - 轻度质量增强（白平衡、高光抑制、锐化）
   - 等比 resize + padding 到模型输入

**验收标准**:
- 预处理管线可对 gallery 图片和 query 图片走相同路径
- 对横版图自动旋转竖卡
- 产出标准化后的图片可目视验收

**测试方法**:
- 用 10 张不同方向/尺寸的图片跑管线，输出前后对比
- 编写单元测试覆盖：横版图、竖版图、小尺寸图、有白边的图

**堵点与风险**:
- OpenCV 的卡片四边形检测对 200px 的低分辨率图效果有限
- 如果卡片本身是横向设计（如 Trainer 卡），方向分类器需要特殊处理

---

### Task 3: Embedding 索引构建

**做什么**:
1. 编写 script_temp/build_index.py
2. 用预处理管线处理所有 9435 张 gallery 图
3. 通过 DINOv2 模型提取 embedding（CLS + mean-pool 拼接，L2 归一化）
4. 用 faiss IndexFlatIP 构建索引
5. 保存 index/embeddings.npy + index/ids.json

**验收标准**:
- 索引文件已产出（9.4k x 768 float32 ≈ 29MB）
- 索引可被加载并用于检索
- 自检：每张图检索自身，top-1 应为自身（score ≈ 1.0）

**测试方法**:
- 运行 build_index.py，检查产出文件
- 写一个快速自检脚本：随机抽 100 张图，检索自身，验证 top-1 命中率 = 100%

**堵点与风险**:
- CPU embedding 耗时：9.4k x 200ms = ~30 分钟
- 如果预处理管线修改了，索引需要重建

---

### Task 4: 阈值校准与拒绝策略

**做什么**:
1. 用基线评估的结果数据校准拒绝阈值 tau 和 margin m
2. 策略：top-1 分数 >= tau 且 top-1 与 top-2 分差 >= m 才接受
3. 在验证集上搜索最优 tau 和 m（最大化 F1 或准确率）
4. 输出校准报告

**验收标准**:
- 已知卡接受率 >= 95%
- 未知卡拒绝率 >= 95%（或误接受率 <= 5%）
- tau 和 m 值已确定并固化

**测试方法**:
- 用留出的 unknown 系列校准
- 绘制 PR 曲线，选择最优点

**堵点与风险**:
- 如果没有真实照片数据，只能用模拟增强数据做校准，跟真实场景有偏差
- 分数分布可能重叠严重（genuine 和 impostor 的 top-1 分数区间有交集）

---

### Task 5: API 服务构建

**做什么**:
1. 用 FastAPI 构建推理服务
2. 接口设计：
   - POST /v1/match：接收 multipart 上传的图片 → 预处理 → embedding → 检索 → 阈值判定 → 返回结果
   - GET /v1/health：健康检查
3. 加载索引和模型（启动时一次加载）
4. 返回格式：{status: "matched"|"rejected", card_id: "xxx", score: 0.xx, margin: 0.xx}

**验收标准**:
- API 可正常启动和响应
- 上传一张模拟图片，能返回匹配结果
- 上传一张非卡图片，能返回 rejected
- 端到端延迟 P95 <= 500ms（CPU）

**测试方法**:
- 用 curl 或 Python requests 测试接口
- 用不同质量/方向/尺寸的图片测试
- 压测：并发 10 请求，观察延迟和正确性

**堵点与风险**:
- CPU 推理延迟：DINOv2 ViT-B/14 单张 ~200ms，整体可能接近 300ms
- 预处理管线需要移植到服务端，保持与离线版一致
- 目前没有 onnxruntime，torch CPU 推理是唯一选择

---

### Task 6: 对比学习微调（M2，需 GPU）

**做什么**:
1. 准备训练数据：对每张 gallery 卡，用模拟增强生成"手机拍照"视图（正对）
2. 用对比学习微调 DINOv2（InfoNCE loss）：
   - 正对：同一张卡的扫描图 vs 模拟拍照图
   - 负例：batch 内其他卡
3. 训练结束后导出 ONNX 模型
4. 重新构建索引（用微调后的模型）

**验收标准**:
- 微调后模型准确率 >= 95%（模拟协议 A）
- 未知卡拒绝率 >= 95%（协议 B）
- 模型已导出为 ONNX 格式

**测试方法**:
- 用微调后的模型重新跑基线评估
- 对比微调前后的 top-1 准确率、分数分布、混淆分析

**堵点与风险**:
- 需要 GPU（单卡 24GB，几小时量级）
- 模拟增强的参数分布（透视扭曲强度、眩光种类、模糊程度）需要精心设计，否则过拟合模拟器
- 如果元数据（系列、卡号）不可得，无法做"同系列硬负例"策略
- 微调后的模型需要重新构建索引，整个流程耗时长

---

### Task 7: 真实照片验收（M3）

**做什么**:
1. 收集 300–500 张真实拍摄的宝可梦卡牌照片（不同设备/光照/角度）
2. 每张照片标注正确的 card_id（或标记为"库外卡"）
3. 用最终的模型 + API 跑验收测试
4. 输出验收报告

**验收标准**:
- 真实照片测试集上 top-1 准确率 >= 95%
- 拒绝准确率 >= 95%
- P95 延迟达标

**测试方法**:
- 写 script_temp/acceptance_test.py
- 逐张照片跑 ID 匹配，统计准确率
- 对错误案例做人工分析

**堵点与风险**:
- 真实照片的收集和标注是最大瓶颈——需要用户配合
- 真实照片可能包含更多"极端情况"：严重眩光、卡片弯曲、手指遮挡、其他卡片背景
- 如果真实照片质量比模拟增强的"最坏情况"还要差，准确率可能骤降

## 四、关键风险与决策点

1. **高分辨率原图**：_200w 后缀暗示存在更高分辨率版本。如果拿到，对准确率是最大的单项提升（卡号、系列标志等细节在 200px 下几乎不可读）。**最高优先级事项**。

2. **GPU 资源**：微调需要 GPU（云单卡 24GB 即可，几小时）。如果 GPU 不可得，M2 阶段无法完成。

3. **真实照片样本**：收集多少、覆盖多少种设备/光照，直接影响验收可信度。

4. **"完全一致"的业务定义**：闪卡/反闪/重印算同一 ID 还是不同 ID？库内是否已区分？如果库内没有区分，模型无法区分。

5. **200px 分辨率的上限**：即使微调后，200px 的输入分辨率可能成为准确率天花板。考虑先出基线数字，如果 baseline 已经低于 80%，则需要认真考虑是否先找高分辨率原图再做后续。
