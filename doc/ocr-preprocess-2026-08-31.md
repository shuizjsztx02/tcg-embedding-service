# OCR 预处理修正与验证（2026-08-31）

## 问题与改动

本次针对 `/v1/ocr`、`/v1/ocr-match`，没有修改 DINO 模型、候选选择或索引。没有重新构建文字索引、切换模型或生成文字细节。

| 已确认问题 | 影响 | 本次处理 |
| --- | --- | --- |
| 依据卡片上下亮度猜测正反方向 | 全图卡、深色卡可能被错误旋转 180° | OCR 不再经过亮度方向函数；比较实际识别结果 |
| 只有文字块少于 2 才重试 180°，且以块数选优 | 多段倒置乱码会直接用于匹配 | 以去重后的可靠字符证据选方向；单字符不参与评分 |
| 两个接口使用不同几何尺寸，ocr-match 连续增强两次 | 结果不一致；细笔画、字距可能被抹掉 | 两接口统一调用 `ocr_pipeline.read_card` |
| 预览在增强/重试前生成 | 倒置预览不一定是实际识别输入，框坐标也不一致 | 从最终选中的 OCR 图像生成预览，框使用该图坐标 |
| 识别器按宽高比排序后，没有还原原始顺序 | 文字与文本框错配，全文顺序错乱 | 将批量结果写回原始 crop 索引 |
| 短文本 batch 未保留模型配置的最小宽度 | 小标题/数字的 padding 偏离参考实现 | 保留 320 的最小宽度；长文本仍按比例扩展 |
| 所有识别结果直接拼接到 BGE | 低置信度乱码污染查询 | 全文保留供核对；查询仅使用置信度 ≥0.75、至少两个字母/数字的文字，按位置排序并去重 |

识别器排序和 padding 规则核对过 [PaddleOCR 官方推理实现](https://github.com/PaddlePaddle/PaddleOCR/blob/main/tools/infer/predict_rec.py)。置信度和本地候选分数均不是校准后的准确率。

## 当前处理过程

1. EXIF 归一化；复用 DINO 已验证的卡片四边形检测和透视几何，但不使用 DINO 的增强与检索逻辑。
2. 卡片校正到 882×1232，再将长边限制为 1200。保留底部边缘，不使用 DINO 的 1% 裁边，以免切掉卡号。极端长宽比输入加边，限制 OCR 检测器按短边放大的开销。
3. 检测到卡片时比较 0°/180°。检测失败时保留原图比较四方向；裁剪结果证据不足时也回退比较原图。
4. 对偏暗、偏亮、低对比度或弱识别结果，尝试一次轻度亮度通道 CLAHE 混合；不再固定去噪、重度锐化、白平衡和重复增强。增强结果需比原始最佳分数高至少 5% 才替换。
5. 方向证据不足时同时比较多个增强方向，不能只增强默认 0°。常见路径两次 OCR，最差路径最多十个候选。
6. 返回选中图像、对应文字框、全文、过滤后的查询以及方向/来源/质量信息。无可靠查询时不调用 BGE，返回空结果和重拍提示。

兼容现有主要响应字段。`/v1/ocr` 新增 `query_text`、`preprocessing`；`/v1/ocr-match` 新增 `full_text`、`preprocessing`。`preprocessed_image` 仍是 JPEG base64，`bbox_space` 为该预览图；旋转角度指相对于透视校正候选（或 EXIF 归一化原图）的逆时针旋转。`ocr_time_ms` 包含方向比较、增强和选择的总耗时。

原有 `preprocess.py` 和 `preprocess_ocr.py` 保留给其他脚本使用。工作区既有亮度函数、日本图库支持及 DINO 标签修改没有被覆盖，也未混入本次提交。

## 实测与限制

测试数据和输出均在本地忽略目录 `script_temp/temp/ocr_preprocess/`，不纳入 Git。对照使用修改前快照：旧几何与双重增强、旧识别器，以及少于两块时重试的完整逻辑，不是只比较旧流程重试前的错误图。

截图裁片仅 299×399，无法代表用户原始相机照片。使用真实 PP-OCRv4 和本地 BGE 模型、现有 59367×384 文字索引。下面七例是**同一照片的受控变体，不是七张独立样本，更不是整体准确率**。

| 截图变体 | 旧查询含可读卡名 | 新查询含可读卡名 | 正确版本 257/182 排名：旧 → 新 |
| --- | --- | --- | --- |
| 0° | 是 | 是（字距缺失） | 4 → 6 |
| 90° | 否，无文字 | 是 | 无 → 1 |
| 180° | 是 | 是 | 4 → 2 |
| 270° | 否，无文字 | 是（字距缺失） | 无 → 6 |
| 亮度 ×0.5 | 是 | 是（字距缺失） | 5 → 8 |
| 亮度 ×1.5 | 否，乱码 | 是 | 49319 → 2 |
| Gaussian blur 0.6 | 是 | 是 | 7 → 1 |

新链路的七例均选择了正向。卡名检查忽略大小写、空白和标点；这不代表逐字识别无误。**原始正向和暗化样本的正确版本排名下降，不能只根据方向修复宣称精确匹配全面提高。** 截图卡号仍低置信且错误，因此未送入匹配；同名版本依然混排。真实接口测试中，原始正向截图 Top-1 为 Regional Championship 同名版本，不是正确的 257/182。

另外人工查看了三张未用于调试的本地照片，各测试正向/倒置：

| 照片 | 结果 |
| --- | --- |
| Duraludon 074/094 | 两方向新旧均正确版本 Top-1；新流程保留 `074/094`，正文仍有字距和个别字符错误 |
| Mega Latias ex 181/132，带评级壳 | 旧正向正确版本第 2、倒置乱码且未进 Top-5；新正向第 3、倒置第 4，并能读出卡名和 `181/132`，尚未做到精确版本 Top-1 |
| 法语 Nidoqueen | 两方向可读卡名；法语重音、正文和卡号仍有误，英文 BGE 与图库语言覆盖是额外限制，不统计精确版本命中 |

单机 CPU 实测：截图七例旧流程中位约 2.0 秒，新约 5.3 秒；三张补充照片六例旧约 2.8 秒，新约 7.8 秒（新范围约 5.8–11.4 秒）。测量存在进程竞争，不是正式性能基准；方向比较的延迟增加需要明确接受和后续优化。

下一阶段应使用人工标注的独立原始照片，分别评估方向、卡名/卡号 CER、精确版本 Recall@5 和延迟。置信度阈值、回退阈值、增强收益阈值目前是保守启发式，尚未校准。PP-OCRv4 的高置信度也可能出错；曝光剪切、反光遮挡、失焦丢掉的信息不能靠 CLAHE 恢复。精确版本识别还需要可靠卡号与系列字段；普通语义 embedding 本身不保证数字版本区分。
