# TCG 卡牌在线识别策略技术方案

> 版本: 2.0 | 日期: 2026-09-03 | 状态: 草案
> 基于: `tcg-match-service`（Docker:8056）、`dino-v3-report.md`、`ocr-v3-report.md`、`dino-v2-final-report.md`、`TCG识别方案V1.0-demo.md`

---

## 1. 背景与目标

### 1.1 现状回顾

V1.0 demo（`TCG识别方案V1.0-demo.md`）已实现两条**相互独立**的匹配链路：

| 链路 | 实测表现（test-images-v3，1945 张真实照片） | 主要弱点 |
|------|------------------------------------------|----------|
| DINO 视觉匹配 | Top-1 准确率 **88.07%**；分数区分力良好 | 92.7% 的错误是"视觉风格相似的不同卡"高分误配 |
| OCR + 文字匹配 | Top-1 准确率 **64.43%**；分数几乎无区分力 | 57.7% 的错误是"同名不同版本"，原理性盲区 |

两条链路的错误模式互补：DINO 看不清"文字差异"，OCR 分不清"同名异版"。这是本方案做**双模态融合 + 分层路由**的数据基础。

### 1.2 目标

构建端到端在线识别管线：**客户端预处理 → 服务端分层匹配 → LLM 兜底**，一次请求返回卡牌身份（productId + 基本信息 JSON）与价格。

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 端到端识别准确率 | ≥ 95% | 承接 PRD 目标；含兜底路径 |
| **误采信率**（把错误的卡当作结果返回） | ≤ 1% | 定价场景的业务红线，优先于召回 |
| 库内卡召回率 | ≥ 98% | 库内卡不应空手而归，兜底路径保证 |
| 端到端延迟 | P50 ≤ 3s / P95 ≤ 8s | GPU 部署 + 分层快速路径（见 §8，CPU 现状无法达标） |
| 高置信直通比例 | ≥ 40% | 决定平均成本与延迟 |

> ⚠️ PRD v1.0 中 "P95 ≤ 500ms" 的指标对含 LLM 与深度模型的管线已不现实，本方案以新指标为准，需产品侧确认。

### 1.3 设计原则

1. **分层漏斗，便宜的路先走**：绝大多数请求应在最快、最便宜的路径上结束；昂贵路径（服务端全量 OCR、LLM 兜底）只留给真正的难例。
2. **双模态交叉验证**：DINO 与 OCR 互为校验信号，不做单模态采信（OCR 分数已被证明不可单独采信）。
3. **价格只来自数据库**：LLM 只负责"认出是哪张卡"，价格永远用 productId 查 `products.jsonl`，杜绝 LLM 编造价格。
4. **兜底保证召回**：双链路均不可信时，用强 VLM 完整识图兜底，确保"总有说法"。
5. **决策留痕**：每次响应携带 `decision_path` 与各阶段分数，支撑离线评估与阈值迭代。

## 3. 阶段一：客户端（2-1 预处理 / 2-2 端侧 OCR）

### 3.1 拍照与 AI 预处理（唯一预处理方）

| 步骤 | 说明 |
|------|------|
| 拍摄引导 | 界面提示单卡、居中、避免强反光与手指遮挡 |
| 卡牌检测 + 透视矫正 | 端侧检测卡面四边形并矫正为正视图（可用 Vision/CoreML 检测模型） |
| 裁剪抠图 | 输出仅含卡面的图像，去除背景 |
| 质量门控 | 模糊度、反光占比、卡面清晰度低于阈值 → **本地拒绝并引导重拍** |

**设计要点**：低质量请求在客户端就被拦截，不消耗服务端 GPU/CPU——这是全链路成本控制的第一道闸。**客户端是唯一预处理方**：质量门控与几何矫正标准须与 `preprocess.py` 的 `assess_quality()`（模糊 Laplacian var < 150、反光比例 > 0.15 等）及矫正参数一致，服务端不做任何二次处理（决策与约束见 §4.0）。

**输出规格**：

| 项 | 规格 |
|----|------|
| 格式 | JPEG，quality 85~92 |
| 分辨率 | 长边 1200~1600px（低于 1024 拒绝） |
| 大小 | ≤ 2MB |
| 方向 | 已做 EXIF 矫正 |

### 3.2 端侧 OCR（暂定）

- **实现**：Apple Vision `VNRecognizeTextRequest`，`recognitionLevel = .accurate`，语言配置 `en-US`、`ja-JP`（按品类可扩展）。
- **执行时机**：与上传准备**并行**执行，超时预算 ~1.5s；超时就放弃附带，不阻塞上传。
- **质量自评**：识别文本块 ≥ 3 且平均置信度 ≥ 0.7 才附带上传，并标记语言；否则不传（服务端会自行降级处理）。
- **定位**：端侧 OCR 是**增强信号而非依赖项**——服务端必须在 `ocr_text` 缺失时完整可用（转用服务端 `pp-ocr-v4`）。

> 是否上传 OCR 文本仍为决策点（§10-①）：收益是省服务端 2~3s OCR 推理；代价是客户端复杂度 + 质量不可控。本方案按"通过质量自评就上传"设计，服务端两种来源都支持。

### 3.3 上传请求

```
POST /v2/recognize  (multipart/form-data)

file            预处理后卡图          (必填)
ocr_text        端侧 OCR 全文         (可选)
ocr_lang        端侧 OCR 语言标识      (可选, 如 "en")
category_hint   用户手选的卡牌品类     (可选; 提供则跳过 LLM 品类判断)
```

`category_hint`（例如 App 内先选"宝可梦/游戏王/…"）可以省掉一次 LLM 调用，建议客户端提供入口，但**不作为必填**。

## 4. 阶段二：服务端管线

### 4.0 服务端边界：不校验、不二次预处理

**决策（已确认）**：输入校验与预处理全部移交客户端（§3.1），服务端信任上传图像，直接进入匹配管线。

- 服务端仅保留模型输入必需的确定性尺寸适配（DINO resize 168×224 + ImageNet 归一化；OCR/BGE 的输入适配）。这属于模型推理步骤，不做任何质量类处理（检测/矫正/增强/门控）。
- 不可解码文件由框架解析失败自然返回 400，不另设业务校验规则。
- **收益**：省去每请求服务端预处理开销（CPU 2~4s），消除客户端-服务端标准分裂；**代价**：精度完全依赖客户端忠实复现预处理参数。
- **分布一致性约束（强制）**：客户端预处理实现须与现 `preprocess.py`（卡牌检测、透视矫正、trim、增强参数，见 V1.0 文档 §5）逐项对齐，参数表随接口契约下发并带版本号。现有全部评测数字（dino-v3 88.07%、ocr-v3 64.43%）基于**服务端预处理**产物；客户端接管后，客户端版本上线前必须用其产物跑对比评估，验收线：top-1 准确率与基线偏差 ≤ 2pp。

### 4.1 S1 LLM 品类判断

**目的**：DINO / 文字索引都是按品类独立构建的（当前服务已配置 `pokemon`、`pokemon_japan`、`magic`、`yugioh`、`onepiece`、`disney_lorcana`、`flesh_blood`、`dragon_ball` 8 个，数据集含 40+ 品类可扩展），必须先定品类才能检索。

| 项 | 设计 |
|----|------|
| 输入 | 低分辨率缩略图（长边 ~512）+ 品类清单 |
| 模型 | 轻量快速多模态模型（qwen-vl-flash 级即可，品类判断是粗粒度任务） |
| 输出 | `{ is_card: bool, categories: [{name, confidence}] }` |
| 取用 | `categories` 取 top-k（k ≤ 2），每个候选品类并行跑 S2，结果合并取最优 |
| 延迟预算 | ≤ 2s。实测本地代理（名义 flash、实际 plus）p50 7.4s 超标，应对见 T-1 |

**路由规则**：
1. 请求带 `category_hint` 且在白名单内 → **跳过 LLM**，直接用 hint（省钱省时）。
2. `is_card = false`（非卡物体）→ 提前返回 `status = not_a_card`。
3. LLM 超时/失败 → 降级：有 `category_hint` 用 hint；否则返回错误提示重试（不做全品类暴力遍历，成本不可控）。

**风险**：品类判错会导致后续检索全在错误索引里进行。缓解：① top-2 品类并行检索，用分数说话；② 品类判断置信度过低（< 0.6）时同样走 top-2 并行。

### 4.2 S2 DINO 视觉匹配

复用 `/v1/dino-match` 内部实现：

```
对每个候选品类:
  方向候选 (竖图: 0°/180°, 横图: ±90°)
  → DINOv2 embed (768-dim, L2 归一化)
  → faiss IndexFlatIP top-5
取跨品类最高分的候选集:
  best_top1, scores[5], margin = score1 - score2
```

`card_id` 格式为 `{productId}_200w`，去后缀即 `productId`，是贯穿全链路的主键。

### 4.3 分层决策（核心）

**阈值参数**（初始值来自 dino-v3 实测，上线前用标注集重新校准，见 §6）：

| 参数 | 含义 | 初始值 | 数据依据 |
|------|------|--------|----------|
| `τ_high` | 高置信采信阈值 | **0.87** | dino-v3：score ≥ 0.85 准确率 97.7%（1114 样本），≥ 0.90 为 98.9% |
| `m_high` | top1-top2 分差 | **0.02** | 沿用现有 `MATCH_MARGIN`，防止双候选胶着时误采 |
| `τ_low` | 低置信分界 | **0.75** | dino-v3：score < 0.75 准确率跌至 68.3%，DINO 不再可信 |

```
best = 跨候选品类最高分结果

if best.score ≥ τ_high and best.margin ≥ m_high:
    → 高置信路径 (§4.3.1)
elif best.score ≥ τ_low:
    → 中置信路径: OCR 重排 (§4.4)
else:
    → 低置信路径: 完整 OCR-match 链路 (§4.5)
```

#### 4.3.1 高置信路径：直接采信

1. 采信 top-1 → `productId` → 查 `products.jsonl` → 基本信息 + 价格，流程结束。
2. **覆盖率与精度预估**（dino-v3 分布）：τ_high = 0.87 时，约 45%~57% 的请求在此直通，路径内准确率 ≥ 97%。真实生产分布（客户端已过滤低质量图）预计覆盖率更高。
3. 可选加固（P1）：若请求恰好带 `ocr_text`，顺手提取卡号与采信卡做一致性检查，矛盾则降级——拦截 ≥ 0.90 区间仍存在的 1.1% 误配。
4. `decision_path = dino_high`。

### 4.4 中置信路径：OCR 重排 DINO Top5

DINO 落在 [τ_low, τ_high) 区间：单看视觉"像，但不敢确定"，典型是风格相似的不同卡——恰是文字信息最能区分的场景。

#### 4.4.1 OCR 文本来源选择

| 策略 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：客户端 OCR 优先（推荐起步） | `ocr_text` 已附带 → 直接用；缺失 → 服务端跑 `pp-ocr-v4` | 省服务端 2~3s CPU | 依赖端侧质量自评 |
| B：服务端始终跑 `pp-ocr-v4` | 与 DINO 并行 | 质量一致可控 | 每请求固定 +2~3s CPU |

推荐 A + B 兜底（决策点 §10-②）。服务端 `pp-ocr-v4` 路径复用现有识别引擎（检测 + 识别，含 180° 倒置重试）；方向矫正与增强由客户端负责，服务端不做二次处理。

#### 4.4.2 重排算法：卡号交叉验证是核心

ocr-v3 报告的第一优化建议：**卡号交叉验证可解决 57.7% 的"同名不同版本"错误**，是性价比最高的信号。

```
1. 从 OCR 文本提取结构化信号:
   - 卡号: 正则匹配 "数字/数字" (如 151/172) 及前缀型编号 (SVP 127 / XY55)
   - 卡名: 通常为首行大写短语
   - 系列码: 如 PR / SVP / SV8a

2. 对 DINO Top5 每个候选, 从 products.jsonl 取:
   customAttributes.number / setCode / productName

3. 逐候选打分调整:
   +0.06  卡号精确一致 (最强信号)
   -0.10  卡号明确矛盾 (OCR 卡号可信但与候选不符)
   +0.02  卡名归一化后一致 (大小写/标点/连字符)
   0      无法提取卡号 → 不动 DINO 原序

   rerank_score = dino_score + Δ
   按 rerank_score 重排

4. 采信判定:
   - top-1 卡号精确一致, 且领先 top-2 ≥ 0.03 → 采信
   - 或重排后 rerank_score ≥ τ_high 且唯一 → 采信
   - 否则 → 降级低置信路径 (§4.5)

5. 特殊分支 — LLM 轻量仲裁 (P1, 可选):
   重排后 top-2 胶着 (差距 < 0.01) → 把卡图 + Top5 候选元信息
   交给轻量 VLM 做"五选一", 比完整识图便宜得多
```

`decision_path = dino_mid_ocr_rerank`。

**明确不做**：不用 OCR embedding 相似度分数参与融合——ocr-v3 已证明该分数对"对错"几乎没有区分力（ok/bad 均值差仅 0.039），只可用其**文本内容**做结构化比对。

### 4.5 低置信路径：完整 OCR-match 链路

DINO < τ_low，视觉已不可信，转文字链路：

```
复用 /v1/ocr-match 内部实现（去掉 preprocess_for_ocr 二次预处理/增强）:
  PP-OCRv4 (检测+识别, 180° 重试)
  → BGE-small encode
  → text-index top-5
```

**采信条件（至少满足一条，OCR 分数本身不作为采信依据）**：

1. **双链路交集**：OCR top-1 的 `productId` 同时出现在 DINO top-5 中，且卡号一致 → 采信（两条独立链路指向同一张卡，置信度高）。
2. **卡号硬匹配**：OCR 提取卡号与 OCR top-1 的 `number` 精确一致，且 top-1 领先 top-2 ≥ 0.03 → 采信。
3. （P1）LLM 仲裁：对 DINO top-5 ∪ OCR top-5 候选集做选择。

满足 → `decision_path = ocr_chain`；全部不满足 → **双链路双低** → 进入 §4.6 兜底。

### 4.6 S3 LLM 完整识图兜底

**定位**：最后的召回保障。只保证"给出答案"，不保证答案直接可信——因此输出必须经数据库校验闭环。

| 项 | 设计 |
|----|------|
| 模型 | 强多模态模型（qwen-vl-max / GPT-4o 级），区别于品类判断用的轻量模型 |
| 输入 | 预处理后原图（长边 1024）+ 结构化抽取 prompt |
| 输出 | 强制 JSON：`{ card_name, set_name, card_number, language, card_type, confidence }`；prompt 约束"不确定就填 null" |
| 超时 | 8s，失败重试 1 次；再失败 → `status = unrecognized` |

**DB 反查（关键设计：LLM 永远不产价格）**：

```
LLM 身份输出
  │
  ├─ card_number + set 在 products.jsonl 精确命中
  │    → productId → 基本信息 + 价格
  │    → status = matched, decision_path = llm_fallback_db_hit
  │
  ├─ 卡号命中但系列歧义 / 仅卡名模糊命中多条
  │    → 返回候选列表 (≤ 5), status = candidates
  │    → 前端展示让用户选择
  │
  ├─ DB 查无此卡 (新卡未入库 / 错版 / 外区卡)
  │    → status = recognized_no_db, in_database = false
  │    → 返回 LLM 识别的身份信息但不带价格, 引导人工收录
  │
  └─ LLM 无法识别
       → status = unrecognized
```

这条"识别归 LLM、价格归数据库"的边界，杜绝了 VLM 幻觉价格直接进入交易场景的风险。

### 4.7 决策路径汇总

| decision_path | 触发条件 | 预期占比* | 精度预期 |
|---------------|----------|-----------|----------|
| `dino_high` | DINO ≥ τ_high 且 margin 达标 | ~45% | ≥ 97% |
| `dino_mid_ocr_rerank` | 中置信 + OCR 重排采信 | ~20% | ≥ 95%（待校准） |
| `ocr_chain` | 低置信 + 文字链路采信 | ~10% | ≥ 95%（待校准） |
| `llm_fallback_db_hit` | 双低 + LLM 识图 + DB 命中 | ~15% | 依赖 DB 命中质量 |
| `candidates` | 歧义候选，交用户选择 | ~5% | 用户保证 |
| `recognized_no_db` | 识别成功但库外 | ~3% | — |
| `unrecognized` / `not_a_card` | 拒绝 | ~2% | — |

\* 占比为基于 dino-v3 分数分布的推算，上线后以实测为准。

## 6. 阈值体系与校准

### 6.1 参数总表

| 参数 | 初始值 | 来源 | 调整方式 |
|------|--------|------|----------|
| `τ_high` | 0.87 | dino-v3 报告 | 标注集校准 |

| `τ_low` | 0.75 | dino-v3 报告 | 标注集校准 |
| 重排加分/扣分 | +0.06 / -0.10 / +0.02 | 经验初值 | 网格搜索 |
| 重排采信 margin' | 0.03 | 经验初值 | 标注集校准 |
| OCR 链采信 margin | 0.03 | 经验初值 | 标注集校准 |
| 品类判断置信度下限 | 0.6 | 经验初值 | 实测调整 |

### 6.2 校准方法与数据

- **已有数据**：`dino-v3-annotations.jsonl`（1945 条，含 verdict/score）、`ocr-v3-annotations.jsonl`（1945 条），可直接用于扫描阈值产出"精度-覆盖率"曲线。
- **校准目标**：选择使 `dino_high` 路径精度 ≥ 98%、且高置信覆盖率 ≥ 40% 的阈值点。
- **持续闭环**：上线后收集用户纠错 → 标注（已有 `annotation_server.py` 基础设施）→ 累积新样本 → 周期性重校准。
- **按品类独立**：阈值先全局共用；数据表明品类间分布差异显著后，按品类维护参数组。
- **已知偏差**：现有评测集以宝可梦为主，其他品类（游戏王/海贼王等）阈值冷启动沿用全局值，上线后优先校准。

## 8. 延迟与成本

### 8.1 分段延迟预算

| 阶段 | CPU 单实例 | GPU | 备注 |
|------|-----------|-----|------|
| 客户端预处理 | 0.5~1.5s | — | 端侧，不占服务端 |
| 上传（~500KB） | 0.3~1s | 同左 | 依赖网络 |
| S1 品类 LLM | 实测 7.4s（代理 plus）/ 目标 ≤ 2s | 同左 | `category_hint` 跳过；模型映射见 T-1 |
| S2 DINO 推理 | 2~4s | **< 0.5s** | 现最大瓶颈：实测 24 并发下平均 24s/张，检索本身仅 1.8s |
| OCR（中/低置信才跑） | 2~3s | ~1s | 客户端 OCR 可替代 |
| BGE + 文本检索 | ~0.2s | 同左 | |
| S3 LLM 兜底（双低才跑） | 2~5s | 同左 | |

**路径延迟估算（GPU 部署）**：高置信 ~1.5~3s；中置信 ~3~5s；最坏路径（兜底）~6~10s。满足 §1.2 目标的前提是 **GPU 部署**——CPU 现状下仅 DINO 推理一项就 2~4s/张，且并发能力仅 ~0.47 img/s（实测），无法支撑在线体验。

### 8.2 成本结构

- **每请求固定成本**：1 次轻量品类 LLM 调用（可被 `category_hint` 省掉）。
- **高置信直通**（预期 ~45%）：无额外成本。
- **中置信**：+1 次服务端 OCR 推理（或 0，用客户端 OCR）。
- **双低兜底**：+1 次强 VLM 调用（最贵）。
- 控制兜底比例 = 控制成本：阈值校准的核心经济目标。

### 8.3 优化方向（按收益排序）

1. **GPU 部署**（DINO 推理提速 ~10 倍，`Dockerfile.gpu` 已备好）。
2. `category_hint` 客户端入口，省品类 LLM 调用。
3. 客户端 OCR 减少服务端 `pp-ocr-v4` 负载。
4. 结果缓存：图像内容 hash（sha1）→ 结果，重复拍摄/同一张卡秒回。
5. 中置信并行化：客户端已带 `ocr_text` 时，重排无需等任何额外推理。

| 指标 | 定义 | 达标线 |
|------|------|--------|

| 高价卡误识别导致错误定价 | 直接业务损失 | 中 | 误采信率 ≤ 1% 硬指标；高置信区间仍存在的 ~1%~3% 误配由卡号交叉检查 + 用户纠错闭环拦截 |
| LLM 品类判错 | 后续链路全部检索错误索引 | 中 | top-2 品类并行；`category_hint` 优先 |
| LLM 兜底幻觉 | 返回不存在的卡信息 | 中 | 强制结构化输出 + "不确定填 null" + DB 反查闸门 + 价格不出 LLM |
| CPU 部署延迟/并发不达标 | 体验不可用 | 高 | GPU 上线为 P0 前置（实测 CPU 0.47 img/s） |
| 阈值过拟合宝可梦评测集 | 其他品类表现差 | 中 | 按品类独立校准；冷启动期该品类结果降一档展示置信 |
| 客户端预处理实现与 `preprocess.py` 参数漂移 | 整体准确率下降（现有评测数字全部基于旧分布） | 中 | 参数表 + 版本号随接口契约下发；客户端版本上线前强制对比评估（与基线偏差 ≤ 2pp，§4.0） |
| OCR 重排帮倒忙（错误卡号干扰正确 DINO 结果） | 中置信精度下降 | 中 | 卡号矛盾仅降权不否决；重排后仍走采信阈值；校准期监控该路径精度 |

## 12. 分阶段实施计划

### P0 — 最小闭环（分层主干 + 兜底）

1. `config.py`：新增阈值与 LLM 配置项
2. `/v2/recognize` 骨架：S1 品类 → S2 DINO → **高/低两档**（暂不做中置信重排，低置信直接进兜底）→ products.jsonl 组装（服务端无 S0，见 §4.0）
3. LLM 品类判断与兜底识图两个调用模块（含超时/重试/降级）
4. `decision_path` 全链路日志
5. **验收**：`test-images-v3` 子集（≥ 300 张）端到端跑通，产出分路径精度报告；误采信率 ≤ 1%

### P1 — 精度提升（中置信重排 + 校准）

1. 中置信路径：`pp-ocr-v4` 重排（卡号提取 + 交叉验证算法）
2. 低置信路径接入现有 `ocr-match` 链 + 采信条件
3. 用 1945 条标注数据校准全部阈值（精度-覆盖率曲线）
4. 高置信路径卡号一致性加固检查
5. **验收**：端到端准确率 ≥ 95%；高置信覆盖率 ≥ 40%；兜底率 ≤ 20%

### P2 — 客户端接入 + 性能

1. 客户端预处理规格对齐 + `ocr_text` / `category_hint` 字段联调
2. GPU 部署切换与压测（延迟分位数 + 并发）
3. 结果缓存（sha1）
4. 用户纠错闭环接入标注平台
5. **验收**：P50 ≤ 3s / P95 ≤ 8s（GPU）；支持并发 ≥ 5 QPS

### P3 — 扩展

1. 多品类铺开（逐品类建索引 + 校准阈值）
2. LLM 轻量仲裁（中置信五选一）
3. 高分辨率图库替换（针对视觉误配集中品类）
4. 价格数据自动同步管线
